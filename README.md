# Play Fingerprint server — GitHub commit storage
---
[Fingerprinter Releases](https://github.com/Riskingfire/fingerprinter/releases)
---
This version replaces PostgreSQL/SQLite with GitHub repository commits. Fingerprints are stored as gzip files under `fingerprints/`; the shared ban list is stored in `banlist.json`. Each fingerprint upload creates a Git commit through GitHub's Contents API. The desktop client can keep using the same Render URL and `API_KEY` because the HTTP API routes are preserved.

## 1. Configure GitHub access

1. Open GitHub Settings → Developer settings → Personal access tokens → Fine-grained tokens.
2. Create a token limited to **only** `Riskingfire/fingerprints`.
3. Give it **Contents: Read and write** permission. No other repository permissions are needed.
4. Add the token to Render as the `GITHUB_TOKEN` environment variable. Never put it in the desktop app or commit it to GitHub.
5. Confirm the repository's default branch is `main`; if not, change `GITHUB_BRANCH` in Render.

The repository can start empty; the server creates `fingerprints/` on the first upload and creates `banlist.json` when the ban list is first changed.

## 2. Deploy on Render

Deploy this folder as a Render web service/Blueprint. Start command:

```bash
gunicorn server:app --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 120
```

Required Render environment variables:

- `API_KEY`: generated by Render (the desktop app uses this key to authenticate to your server). Always an admin key. Add `API_KEY1`, `API_KEY1_PERM`, ... for restricted keys (see section 4).
- `GITHUB_TOKEN`: fine-grained token described above.
- `GITHUB_REPO`: `Riskingfire/fingerprints`.
- `GITHUB_BRANCH`: `main` (or your actual default branch).

There is no `DATABASE_URL`, PostgreSQL service, or psycopg dependency in this version.

## 3. Configure desktop app

In Play Fingerprint → **Server...**, set the Render service URL and the Render `API_KEY`. The `GITHUB_TOKEN` is only used by the server and must not be entered into the desktop app. Test the connection and then upload a fingerprint.

## 4. API keys and permissions

**Nothing to change for existing setups.** Your current `API_KEY` keeps working and is treated as an admin key, so the desktop app does not need updating.

### Permission numbers

Permissions work like Discord's: each one is a power of two, you add up the ones you want, and the total decodes back to exactly that set. (Plain prime numbers would not work for this, because e.g. 2 + 3 = 5 is also a prime, so a total could mean several different things. Powers of two never collide.)

| Value | Name | Allows |
|------:|------|--------|
| 1 | `ADMIN` | **Everything**, including permissions added later |
| 2 | `VIEW_STATUS` | `GET /api/status` |
| 4 | `READ_FINGERPRINTS` | list, search, inspect, download fingerprints |
| 8 | `UPLOAD_FINGERPRINTS` | upload / overwrite fingerprints |
| 16 | `DELETE_FINGERPRINTS` | delete fingerprints (single + bulk) |
| 32 | `READ_BANLIST` | view the ban list, check one name |
| 64 | `MANAGE_BANS` | add / remove bans |
| 128 | `RUN_ANALYSIS` | similarity analysis |
| 256 | `MANAGE_KEYS` | create / edit / revoke API keys (only up to your own permissions) |

Examples: read-only = 2 + 4 + 32 = **38**; desktop uploader = 2 + 4 + 8 = **14**; moderator = 2 + 4 + 32 + 64 + 128 = **230**; admin = **1**.
You can also write names instead of a number: `API_KEY1_PERM=read_fingerprints,upload_fingerprints,view_status`.
`GET /api/permissions` returns this table, and `GET /api/me` tells a key what it can do.

### Option A: keys in Render environment variables

```
API_KEY1       = <long random secret>
API_KEY1_PERM  = 14
API_KEY1_NAME  = desktop uploader        (optional label for logs and commit messages)
API_KEY2       = <another secret>
API_KEY2_PERM  = 38
```

Add as many as you like (`API_KEY3`, `API_KEY4`, ...). A numbered key with no `_PERM` defaults to read-only (38). An invalid `_PERM` makes the deploy fail on purpose, so a typo can never silently give out the wrong access. Changing environment variables restarts the service on Render.

### Option B: create keys on the fly (no redeploy)

An admin (or any key with `MANAGE_KEYS`) can mint keys through the API:

```bash
curl -X POST https://YOUR-APP.onrender.com/api/keys \
  -H "Authorization: Bearer $ADMIN_KEY" -H "Content-Type: application/json" \
  -d '{"name": "friend bot", "permissions": 12}'
```

The response contains the new secret (starts with `pfk_`) **once**. Only a SHA-256 hash is stored, in `apikeys.json` in the repository. Manage them with:

- `GET /api/keys` list keys (never shows secrets)
- `PATCH /api/keys/<id>` change `name` and/or `permissions`
- `DELETE /api/keys/<id>` revoke

Keys defined in environment variables show up in the list but can only be changed in Render. Keys with `MANAGE_KEYS` but not `ADMIN` can only hand out permissions they hold themselves, and can't edit or revoke keys stronger than their own.

## 5. API reference

All routes except `/health` need `Authorization: Bearer <key>`. Missing/invalid key gives `401`; a valid key without the needed permission gives `403` and says which permission is missing.

| Route | Permission | Notes |
|-------|-----------|-------|
| `GET /health` | none | |
| `GET /api/me` | any key | which key am I, what can it do |
| `GET /api/permissions` | any key | permission table |
| `GET /api/status` | `VIEW_STATUS` | |
| `GET /api/fingerprints[?q=text]` | `READ_FINGERPRINTS` | `q` filters by name (new) |
| `GET /api/fingerprints/<name>/info` | `READ_FINGERPRINTS` | **new**: size, windows, features, banned? |
| `GET /api/fingerprints/<name>` | `READ_FINGERPRINTS` | download |
| `PUT /api/fingerprints/<name>` | `UPLOAD_FINGERPRINTS` | |
| `DELETE /api/fingerprints/<name>` | `DELETE_FINGERPRINTS` | |
| `POST /api/fingerprints/bulk-delete` | `DELETE_FINGERPRINTS` | **new**: `{"names": [...]}`, max 25 |
| `POST /api/fingerprints/<name>/rename` | `UPLOAD_FINGERPRINTS` + `DELETE_FINGERPRINTS` | **new**: `{"new_name": "..."}`; does not move bans |
| `GET /api/banlist` | `READ_BANLIST` | |
| `GET /api/banlist/<name>` | `READ_BANLIST` | **new**: is this name banned? |
| `PUT /api/banlist/<name>` | `MANAGE_BANS` | |
| `DELETE /api/banlist/<name>` | `MANAGE_BANS` | |
| `POST /api/analysis` | `RUN_ANALYSIS` | |
| `GET/POST /api/keys`, `PATCH/DELETE /api/keys/<id>` | `MANAGE_KEYS` | **new** |

Every write is attributed in the commit message (`[by <key name>]`) and in the server log, so Git history doubles as an audit trail.

## Repository layout

- `fingerprints/<profile-name>.json.gz` — each uploaded profile, committed separately.
- `banlist.json` — shared ban entries, committed when updated.
- `apikeys.json` — runtime-created API keys (hashes only), committed when keys change.

## Important considerations

- The repository contents and Git history may be visible to anyone if the repository is public. Fingerprints are behavioral biometric-like data. Only upload profiles with informed authorization; consider making the repository private.
- Runtime keys are stored as hashes, but `apikeys.json` still reveals key names and permissions in a public repo. Prefer a private repository.
- A GitHub token with write access can change this repository. Keep it in Render's secret environment variables and rotate it if exposed.
- Each profile update creates a commit. Avoid frequent uploads of the same profile; enable auto-upload only if this commit volume is acceptable.
- GitHub Contents API responses are expected to include base64 content, which is supported for files up to 1 MB. Keep compressed fingerprint files under 1 MB.
- Server-side matching is heuristic only and must not automatically trigger bans; review potential matches manually.
